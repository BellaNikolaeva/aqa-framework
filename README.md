# AQA Framework — Book Tracker API

Фреймворк для автоматизации API-тестирования, написанный с нуля на Python.
Целевой объект тестирования — [Book Tracker API](https://github.com/BellaNikolaeva/book-tracker-api),
мой собственный backend-проект на Django REST Framework.

## Зачем этот проект

Существующий опыт автоматизации был встроен в чужой существующий фреймворк
на текущей работе. Этот проект — архитектура, инструменты и решения выбраны
и реализованы самостоятельно с нуля: от структуры клиентов до CI-пайплайна,
с оглядкой на актуальные (2026) практики Python API-автоматизации, а не
только на то, что я уже знала.

Риск-ориентированная тест-стратегия (что тестируется в первую очередь и
почему, что сознательно вне периметра, как менялись предположения по
ходу дела) — отдельно, в [`docs/test-strategy.md`](docs/test-strategy.md).

Полная хронология создания фреймворка — инструменты, команды, найденные
баги и как они решались, готовые кейсы для собеседования — в
[`docs/project-journal.md`](docs/project-journal.md).

## Архитектура

```
clients/     — API-клиенты по одному на ресурс (Auth, Books, MyBooks, Tags),
               наследуются от BaseClient — аналог Page Object, но для API
schemas/     — Pydantic-модели ожидаемого контракта ответов
tests/       — тесты по ресурсам (smoke/regression), security-смоук
               (test_security.py), пагинация, контрактный набор на
               schemathesis (test_contract.py)
utils/       — генератор тестовых данных (Faker)
config/      — типизированные настройки (pydantic-settings)
docs/        — риск-ориентированная тест-стратегия (test-strategy.md),
               реальная OpenAPI-схема (Book_Tracker_API.yaml) и полная
               хронология создания проекта (project-journal.md)
locustfile.py — read-only нагрузочный смоук на каталог книг
```

## Ключевые решения и почему именно так

- **Pydantic-модели вместо голого JSON Schema** для валидации ответов
  (`schemas/models.py`). Модель одновременно и проверяет контракт, и даёт
  типизированный объект для дальнейших assert'ов в тесте — без риска
  `KeyError` на опечатке в имени поля.
- **Типизированный конфиг через `pydantic-settings`** вместо `os.getenv` —
  невалидный `AQA_BASE_URL` падает сразу с понятной ошибкой при старте,
  а не где-то в середине прогона.
- **Фикстура-фабрика вместо фикстуры-значения** (`many_books` в `conftest.py`)
  для тестов, которым нужно переменное число объектов — распространённый
  паттерн для параметризуемого сетапа.
- **Изоляция через маркер, а не через "чистую" БД.** Каталог книг в этом
  API общий, не привязан к пользователю (в отличие от личной библиотеки) —
  значит тесты пагинации не могут полагаться на `count` всего каталога.
  Каждый тест помечает свои книги уникальным префиксом в названии и
  фильтрует по нему через `search` — это и корректность, и безопасность
  при параллельном прогоне (`pytest -n auto`), проверено на 4 воркерах.
- **Mutation testing (`mutmut`)** — не "сколько строк покрыто", а "ловят ли
  тесты реальные баги, если код специально сломать". Проверяет `clients/`
  (чистая логика payload/params/роутинга, без сетевых сайд-эффектов) на
  smoke-раннере, чтобы не гонять против реального Render часами. Первый же
  прогон нашёл выжившего мутанта: `test_search_tag_by_name` проверял только
  "искомый тег есть в списке" — это истинно, даже если фильтрация вообще
  не работает и API возвращает все теги без разбора. Переписала тест на
  явную проверку присутствия совпадения И отсутствия заведомо несовпадающего
  тега — вручную применила мутацию, подтвердила, что новый тест её ловит.

- **Security-смоук — не пентест, а дешёвые проверки типичных дыр.**
  Отдельный файл `test_security.py`: сломанная аутентификация (мусорный
  токен, испорченная подпись, не-Bearer схема), IDOR на прямой доступ по
  id (не только через список, как в `test_user_isolation`), инъекции в
  поисковые параметры. Разработка этих тестов на локальном моке сразу же
  поймала дыру в самом моке: наивная проверка токена по префиксу
  ложно считала подделанный токен валидным — пришлось переделать
  мок на честную сверку с реально выданными токенами, а не с шаблоном.

- **Ретраи через `tenacity`** на уровне `BaseClient` — специально под
  Render free tier, который "засыпает": обрывы соединения и 502/503
  ретраятся автоматически, вместо падения теста на первом холодном старте.
- **`@pytest.mark.parametrize` вместо копипасты** для однотипных негативных
  кейсов (отсутствие каждого обязательного поля по очереди) — параметризация
  сразу же поймала реальный баг: мок-сервер для локальной проверки
  фреймворка изначально проверял только одно обязательное поле из трёх.
- **Контрактные тесты на `schemathesis`** (`tests/test_contract.py`) — вместо
  вручную придуманных кейсов инструмент читает реальную OpenAPI-схему
  (её отдаёт `drf-spectacular`) и сам генерирует валидные и граничные запросы,
  проверяя, что сервис не падает с 500 и отвечает по заявленному контракту.
  Не входит в smoke/regression: схема грузится уже на этапе сбора тестов,
  поэтому вынесена в отдельный CI-шаг (nightly), чтобы не ронять обычный
  прогон при недоступности сети.
- **`pytest-xdist` — не по умолчанию, а по команде.** Тесты изолированы
  через случайные данные на каждый тест (`registered_user` регистрирует
  нового пользователя), поэтому параллельный прогон в принципе безопасен —
  но против реального Render с его холодным стартом он не всегда ускоряет
  прогон и усложняет чтение упавших тестов, поэтому включается явно
  (`pytest -n auto`), а не молчаливо для каждого запуска.
- **`--strict-markers`** в конфиге — опечатка в `@pytest.mark.smoke`
  падает как ошибка конфигурации, а не тихо игнорируется.
- **Конфиг консолидирован в `pyproject.toml`** (pytest + ruff) вместо
  отдельных `pytest.ini`/`setup.cfg`.
- **Allure-отчётность**: каждый HTTP-запрос/ответ прикрепляется к отчёту
  автоматически через `_attach_to_allure` в `BaseClient`.
- **Teardown через фикстуры.** `created_book` удаляет книгу после теста —
  прогон не оставляет мусор в БД задеплоенного сервиса.

- **Сверено с реальной OpenAPI-схемой** (`docs/Book_Tracker_API.yaml`,
  экспортирована из `/api/schema/`), а не только с описанием в README
  целевого проекта. Сверка нашла и исправила реальные расхождения:
  `genre` — не обязательное поле и не enum (просто строка), ответ
  `POST/GET/PATCH /api/my-books/` содержит вложенный объект `book`,
  а не `book_id` (тот только для записи), `rating` ограничен диапазоном
  1–5, статусы — `want_to_read/reading/finished/dropped`. Заодно нашли
  баг в самой схеме: `/api/my-books/stats/` документирован как
  возвращающий `UserBook`, хотя по описанию это агрегированная
  статистика — несовпадение, которое стоит показать команде разработки.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env

pytest                        # весь набор (smoke + regression), последовательно
pytest -m smoke               # только критичные проверки
pytest -m regression          # полный regression
pytest -n auto                # параллельно, по числу ядер — по команде, не дефолт
pytest tests/test_contract.py # контрактные тесты против реальной OpenAPI-схемы

allure serve allure-results   # интерактивный HTML-отчёт
```

## История прогонов (Allure + GitHub Pages)

CI не просто показывает результат последнего прогона — публикует полную
историю на GitHub Pages: тренд по сборкам, длительность, стабильность
конкретных тестов во времени, а не только "зелёно/красно сейчас".

Публикуется только с `main` (не с PR-веток — незачем зашумлять общий
тренд отчётами по недомерженному коду, и у форков всё равно нет прав
писать в `gh-pages` этого репозитория).

**Разовая настройка (руками, workflow это сделать не может):**
1. Запусти workflow хотя бы раз с `main` (push или вручную) — появится
   ветка `gh-pages`
2. Settings → Pages → Source: `Deploy from a branch` → ветка `gh-pages`,
   папка `/ (root)`
3. Ссылка на отчёт появится там же в Settings → Pages

## Нагрузочный смоук (Locust)

Один сценарий на каталог книг — read-only, без токена, не оставляет
данных в общей БД. Симулирует посетителя, который листает, ищет и
открывает карточки книг.

```bash
# интерактивно, с UI на localhost:8089
locust -f locustfile.py --host https://book-tracker-api-frnm.onrender.com

# headless-отчёт (например, перед релизом)
locust -f locustfile.py --host https://book-tracker-api-frnm.onrender.com \
    --users 10 --spawn-rate 2 --run-time 30s --headless \
    --csv reports/load-test --html reports/load-test.html
```

В CI это отдельная джоба `load-test`, запускается только вручную
(Actions → Run workflow) — не на каждый push и не по расписанию: это
реальная нагрузка на чужой бесплатный сервис (Render free tier), гонять
её молча в фоне на каждый коммит неуместно.

Осознанно не тестирует запись (создание книг/my-books): нагрузочный
прогон на POST-эндпоинты плодил бы мусорные данные в общем каталоге при
каждом запуске — вместо этого можно поднять сценарий против локального
мок-сервера, если нужно нагрузить именно write-путь.

## Видимость flaky-тестов

`pytest-rerunfailures` сам по себе просто тихо перезапускает упавший тест —
итоговый прогон становится зелёным, и никто не узнаёт, что конкретный тест
на самом деле нестабилен. Это осознанно не то же самое, что "тест
починили": флаки прячется, а не исчезает.

Решение в `tests/conftest.py` (хуки `pytest_runtest_logreport` +
`pytest_terminal_summary`): любой тест, прошедший только со второй попытки,
явно попадает в отдельную секцию терминального вывода и в `flaky-tests.json`
— не молча растворяется в общей зелёной статистике.

```bash
pytest -m smoke --reruns 2 --reruns-delay 5   # ретраи — по флагу, не дефолт
cat flaky-tests.json                          # список нестабильных тестов
```

Ретраи включены **только в CI против реального Render** (`--reruns` в
`ci.yml`), где сетевая нестабильность и холодный старт — реальный источник
случайных падений, не связанный с багами тестов. Локально по умолчанию
ретраев нет — падение должно быть видно сразу, без маскировки во время
отладки. В CI список flaky-тестов дополнительно поднимается как
GitHub Actions warning-аннотация и грузится как отдельный артефакт.

## Mutation testing

```bash
mutmut run              # прогон против clients/ (нужен доступный API — мок или боевой)
mutmut results          # список мутантов: killed/survived/no tests
mutmut show <id>        # диф конкретного мутанта
```

Раннер использует smoke-маркер для скорости — часть мутантов помечается
"no tests" (не покрыты именно smoke-набором, не значит "не протестированы
вообще"). `mutants/` — рабочая песочница mutmut, не коммитится (в `.gitignore`).

## Линт и форматирование

```bash
ruff check .           # линт: pyflakes, pycodestyle, isort, bugbear, simplify, comprehensions
ruff check . --fix     # автофикс того, что чинится автоматически
ruff format .          # форматирование
ruff format --check .  # проверка форматирования без изменений (то же, что в CI)
```

Опционально — `pre-commit install`, чтобы `ruff` гонялся автоматически перед
каждым коммитом, а не только в CI (конфиг уже есть в `.pre-commit-config.yaml`).

## Запуск через Docker

Без локального Python и виртуального окружения — нужен только Docker.

```bash
docker compose up smoke        # быстрые проверки
docker compose up regression   # полный набор
docker compose up contract     # контрактные тесты против реальной схемы
docker compose up mutation     # mutmut run внутри контейнера
docker compose up load-test    # Locust, headless, 30 сек, отчёт в ./reports

# конкретный файл/маркер вручную, без docker-compose:
docker build -t aqa-framework .
docker run --rm aqa-framework pytest -m smoke
```

`AQA_LOCUST_HOST` в `.env` переопределяет цель для `load-test` (по
умолчанию — боевой Render), например на локальный мок.

Отчёт `load-test` (`.html`/`.csv`) остаётся на хосте в `./reports` — том
проброшен из контейнера, как и `allure-results`.

`.env` не обязателен — без него используются дефолты из `config/settings.py`
(боевой Render-адрес). Нужен только чтобы переопределить `AQA_BASE_URL`
(например, на локальный сервер, доступный из контейнера как
`http://host.docker.internal:8000` на Mac/Windows).

Результаты Allure остаются на хосте в `./allure-results` — том проброшен
из контейнера, отчёт не пропадает вместе с ним.

CI отдельно проверяет, что образ вообще собирается и smoke-тесты проходят
внутри контейнера (`docker` job в `.github/workflows/ci.yml`) — ловит
поломку Dockerfile до того, как её найдёт кто-то другой.

## Что покрыто

- Аутентификация: регистрация, логин, refresh-токен (позитив + негатив,
  включая параметризованную проверку каждого обязательного поля)
- Каталог книг: CRUD, поиск, фильтры (жанр, тег, диапазон года издания),
  прикрепление тегов через `tag_ids` при создании, валидация схемы через
  Pydantic, доступ без токена
- Пагинация каталога: граница страницы, ссылки next/previous, соответствие
  count реальному числу объектов (изолировано от прочих данных в общем
  каталоге через уникальный маркер в названии — безопасно при параллельном
  прогоне)
- Личная библиотека: статусы чтения, оценки (включая границы 1-5), заметки,
  даты начала/окончания чтения, бизнес-правило "оценка только для
  прочитанных", уникальность записи, изоляция данных между пользователями,
  добавление несуществующей книги (400), недопустимый статус (400), доступ
  без токена (401)
- Теги: CRUD, поиск, дубликат имени, несуществующий тег, доступ без токена
- Контрактное соответствие реальной OpenAPI-схеме (schemathesis)
- Security-смоук: сломанная аутентификация (синтаксически некорректный
  токен, подделанная подпись, неверная auth-схема, пустой Bearer), IDOR
  (прямой доступ/изменение/удаление чужой записи my-books по id — 404,
  не 403, чтобы не подтверждать факт существования чужих данных),
  инъекции в поисковые параметры (SQL-паттерны, XSS-пейлоад как обычный
  текст без падения сервера)

61 юнит/интеграционный тест, полностью зелёные — проверено локально против
мок-сервера, имитирующего контракт реального API (сверенный построчно
с `docs/Book_Tracker_API.yaml`); прогон против реального Render-сервиса —
через CI или `AQA_BASE_URL` в `.env`.
